=======================================================

1. ARQUITECTURA
---------------

Kapso se usa solo como transporte de WhatsApp. La conversación vive en el CRM:

  WhatsApp -> webhook /webhooks/kapso -> cola whatsapp_messages -> worker
           ^                                                   |
           |                                                   v
        KatyResponder (reglas)  <---------------------  respuesta

- src/app/webhooks/kapso/route.ts: valida la firma HMAC-SHA256, deduplica por
  message.id, guarda el mensaje entrante, genera la respuesta, aplica acciones
  y encola el envío en la misma transacción.
- src/lib/whatsapp.ts: normalización de teléfonos, alta automática de contactos
  desconocidos, contexto de propiedad, acciones (agente/visita) y cola de envío
  con reintentos y tope de intentos.
- src/lib/katy.ts: respuestas por reglas para precio, ubicación, requisitos,
  descripción, visita y agente.
- scripts/worker.ts: procesa la cola cada ~3 segundos y la sincronización con el
  portal cada 60 segundos.
- PORTAL-LAB: tras enviar la consulta muestra el botón wa.me con el mismo número
  que usa el CRM.

No hay que crear preguntas y respuestas en el workflow de Kapso. El workflow
"Respuesta basica" solo tiene trigger en el sandbox, así que no interfiere con
el número de producción; se deja activo.


2. VARIABLES DE ENTORNO (CRM-LAB/.env.local)
--------------------------------------------

Obligatorias para WhatsApp:

- KAPSO_API_KEY: API key de Kapso.
- KAPSO_PHONE_NUMBER_ID: phone_number_id de Meta de la línea conectada.
  Tiene prioridad sobre KAPSO_SANDBOX_PHONE_ID.
- KAPSO_WEBHOOK_SECRET: secreto que devuelve Kapso al crear el webhook. Debe
  ser el mismo que usa Kapso para firmar X-Webhook-Signature.

PORTAL-LAB/.env.local:

- NEXT_PUBLIC_WHATSAPP_NUMBER: número público en formato internacional sin "+".
  Debe coincidir con la línea conectada en el CRM.


3. PUESTA EN MARCHA LOCAL
-------------------------

1. Base de datos (Docker):

     docker start crm-db

2. Migraciones:

     npm run migrate

   Aplica 001-initial y 002-whatsapp.

3. Aplicación:

     npm run dev

4. Worker (en otra terminal):

     npm run worker:dev

   Procesa la cola de WhatsApp y la sincronización con el portal.

5. Exponer HTTPS para que Kapso entregue eventos (túnel o dominio real) y
   registrar el webhook config-level:

     node .agents/skills/integrate-whatsapp/scripts/create.js \
       --url https://TU-DOMINIO/webhooks/kapso \
       --phone-number-id 1404393919431625 \
       --scope config \
       --events whatsapp.message.received \
       --payload-version v2 \
       --buffer-enabled true \
       --buffer-window-seconds 3

   Guardar el secret_key que devuelve Kapso en KAPSO_WEBHOOK_SECRET.

6. Verificar:

     node .agents/skills/integrate-whatsapp/scripts/list.js \
       --phone-number-id 1404393919431625 --scope config


4. COMPORTAMIENTO
-----------------

- Contacto conocido: se responde con los datos de la propiedad consultada.
- Número desconocido: se crea un contacto (tipo comprador) y se responde. Queda
  registrado en auditoría como whatsapp.contact_created.
- Consulta del portal: importInquiry guarda whatsappPropertyId en el contacto
  para que el bot responda por esa propiedad y no por la última oportunidad.
- Visita: pide día y horario, crea una actividad tipo "visit" y deja la nota.
- Agente: agrega una nota al contacto y registra auditoría.
- Deduplicación: el mismo message.id no se procesa dos veces ni genera doble
  respuesta.
- Ventana de 24 horas: Meta solo permite texto libre si el cliente escribió
  primero. Un envío fuera de ventana queda como error 422 y se reintenta con
  backoff hasta un tope de 8 intentos; después se marca "failed".
- Al importar una consulta del portal se encola un saludo proactivo. Si el
  cliente todavía no escribió, ese saludo cae en la ventana de 24 h y se agota
  por el tope de reintentos; la conversación real empieza cuando el cliente
  escribe.
- Errores permanentes (400, 401, 404, 413, 403 de autenticación) no se
  reintentan indefinidamente.


5. PRUEBA LOCAL SIN KAPSO
-------------------------

Se puede simular el webhook con una firma HMAC del body crudo:

  X-Webhook-Signature: HMAC-SHA256(KAPSO_WEBHOOK_SECRET, body) en hex

Payload mínimo v2:

  {
    "message": {
      "id": "wamid.prueba.1",
      "timestamp": "1794544437",
      "type": "text",
      "text": { "body": "precio" },
      "kapso": { "direction": "inbound", "status": "received", "content": "precio" }
    },
    "conversation": {
      "id": "conv_prueba",
      "phone_number": "541167062068",
      "phone_number_id": "1404393919431625",
      "kapso": { "contact_name": "Guillermo" }
    }
  }

Resultado esperado: HTTP 200 con processed=1; el reenvío del mismo id devuelve
duplicates=1 y no encola otra respuesta.
